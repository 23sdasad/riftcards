## 目标与背景

Phase 1 目前只有一条高层路线图，尚无按依赖排序的执行任务、可判断的验收边界和关键产品决策。本任务负责把“本地完整对局”拆成可逐项交付的纵向任务，先确认交互、优先顺序和端到端验收方式，再进入实现。

当前基线：

- Go 引擎已包含 8 张 MVP 卡牌定义和出牌、攻击、结束回合、认输流程。
- 引擎测试已覆盖开局、回合归属、单位召唤、守卫、伤害法术和隐藏手牌，但未逐卡覆盖全部规则和完整事件序列。
- WebSocket、房间、C# Core 会话和协议 DTO 已有骨架。
- Godot 客户端目前是单文件诊断界面，法术和攻击目标由代码自动选择，尚未提供玩家选目标、合法操作提示、错误反馈或事件动画队列。
- 尚无自动化的本地端到端完整对局验证。

## 范围与非目标

交付：

- 确认 Phase 1 的第一验收目标、Godot 交互形态和端到端验证范围。
- 以底层优先为原则，先安排路径、命令外壳、显式状态机和指令处理链路，再接客户端表现层。
- 将 Phase 1 拆成有编号、依赖、状态和可检查验收标准的执行任务。
- 明确每项任务的测试、协议样例、日志或人工验证证据。
- 必要时更新 `ai-docs/product/roadmap.md`，但只记录已确认的顺序和范围。

非目标：

- 本任务不实现卡牌规则、Godot 对局界面、动画或网络恢复。
- 不提前进入 Phase 2 的凭证、重连、幂等和事件日志落盘。
- 不引入美术资源、正式品牌视觉或客户端预测。

## 前置条件与待决策

已确认决策：

1. `path` 同时覆盖工程与资源路径治理、网络到引擎的指令路径，并要求在 Windows、macOS、Linux 上使用一致的路径语义。
2. `shell` 主要是跨平台指令进程层，负责启动、输入输出、退出状态和终止管理；Godot 应用壳在 UI 任务中处理。
3. 状态机先覆盖对局与回合生命周期；单条指令的校验和结算路径单独建立任务。

Phase 1 先完成底层任务，Godot 对局 UI、动画和视觉表现排在这些任务之后。UI 的具体形态和端到端验收方式在底层边界确认后再定。

工具链待确认：当前主机没有 `task`、Go、.NET SDK 和 Godot。执行类任务开始前，必须先具备可运行的完整门禁；只写代码但不能验证的任务不得标为 `done`。

## 风险与回退

主要风险是先确定 UI 形态再补测试，会放大引擎规则错误；或先做大量测试却不形成可操作纵切，延迟产品反馈。回退方式是按已确认的第一验收目标重排任务，不删除未开始任务的编号，改标 `planned` 或 `deferred`。
