## 目标与背景

当前只能联机：两个客户端各占一个座位，凑不齐人就没法玩，也无法在无人配合时验证完整对局（端到端测试用的是脚本化客户端，不是可玩的对手）。本任务设计**单机模式**：玩家一个人开局，对手是服务端托管的 AI，并提供**简单、普通、困难**三档难度。

已实现（可直接复用）：权威结算与指令路径（005/006）、规则与事件（007）、投影裁剪（`ViewForSeat`）、可重复的端到端验收（010）、可操作的客户端界面（016）。

设计假设（待实现验证）：AI 作为服务端内的一个 `match.Peer` 参与对局，因此不需要改动 `game` 规则层，也不需要新增结算路径。

## 设计

### 核心决策：AI 在服务端，作为普通 Peer

三种可选做法与取舍：

| 做法 | 结论 |
| --- | --- |
| 客户端内实现 AI | **否决**。AI 是对手，需要对手手牌才能决策，而客户端禁止持有对手隐藏信息；让客户端托管对手等于把权威交回客户端。 |
| 服务端 AI 直接改权威状态（"快捷结算"） | **否决**。会出现第二条结算路径，绕过校验、事件与回放，破坏"服务端先校验再结算"的单一事实来源。 |
| 服务端 AI 作为 `match.Peer`，通过 `Manager.Submit` 提交指令 | **采用**。AI 拿到的是自己的投影，提交的是普通指令，走与人类完全相同的校验、结算、广播与事件日志路径；`game` 层零改动，回放天然可用。 |

推论：

- **AI 不拥有隐藏信息**：只读 `ViewForSeat(aiSeat)`，与人类客户端收到的投影完全一致。
- **难度来自决策质量，不来自信息优势**：任何难度都不得读对手手牌、牌库顺序或未来随机数。
- **客户端无法伪造难度**：难度由服务端记录在对局里并写入投影，日志同时记录，便于审计。
- **AI 可被测试**：`botPeer` 与现有 `fakePeer` 同构，策略是纯函数（投影 → 指令），无需网络即可单测。

### 组件与依赖方向

```text
server/internal/bot
  ├─ Bot 接口：Decide(view, seat) (PlayerCommand, bool)
  ├─ easy / normal / hard 三个策略
  └─ botPeer：实现 match.Peer（收件箱 + 驱动 goroutine + 提交指令）
```

- `bot` → `game`（读投影与指令类型）、`protocol`（信封）、`metrics`（计数）。
- `match` → `bot`：单机模式下建房时把 `botPeer` 放到座位 1。
- `game`、`protocol` **不依赖** `bot`（依赖方向不变）。

`botPeer` 的关键约束：

1. **独立 goroutine 驱动**，不在 `Send` 里同步提交：`Send` 可能被房间广播调用，同步提交会重入结算。
2. **动作预算**：每回合最多 N 条指令（默认 32），被拒绝的动作不再重试，防止拒绝风暴与死循环。
3. **思考延迟**：默认 600ms（测试为 0），仅影响节奏，不影响决策内容。
4. **确定性**：RNG 由对局种子派生（`seed ^ turn ^ seat ^ 常量`），不读系统时间、不读全局随机源。
5. **可取消**：对局结束或连接断开时驱动 goroutine 退出。

### 三档难度

共同点：只看自己的投影；只提交合法意图；每回合结束前一定会结束回合（不会卡住对局）。

**简单**

- 策略：随机合法动作。费用够的牌里随机挑一张；法术随机指向对手英雄或某个单位；可攻击单位随机挑目标（可能忽略守卫，被拒后改打守卫）；否则结束回合。
- 特征：会漏斩杀、会做亏本交换、偶尔把法术浪费在满血目标上。
- 定位：新手能赢，行为可预期。

**普通**

- 策略：按优先级的启发式贪心。
  1. **斩杀**：可攻击单位总攻击 ≥ 对手英雄 HP 且无守卫阻挡 → 全部打脸。
  2. **解场**：优先完成"能击杀且不被反杀"或"换到更高价值"的交换；对手有守卫时先处理守卫。
  3. **铺场**：按费用利用率出牌（在剩余费用内选总价值最高的一组），己方英雄 HP 偏低时优先守卫。
  4. **直伤**：对手英雄 HP ≤ 法术伤害且无更优解场时，用法术收尾。
- 特征：会斩杀、会做价值交换、不会无谓浪费。

**困难**

- 策略：普通策略 + **有限搜索**。
  - 对本回合的动作序列做有界 DFS/beam（节点上限默认 2000、深度 ≤ 8），叶子用启发函数评分：
    `4×(对手英雄HP − 己方英雄HP) + 3×(对手场面价值 − 己方场面价值) + 1×(手牌差) + 0.5×能量利用率`，场面价值 = Σ(攻击 + 生命 + 守卫加成)。
  - 对"下回合可能被斩杀"的线扣分（浅层评估对手最强回应）。
  - 搜索内找到必胜线时优先执行（先解守卫再打脸这类组合会自然出现）。
  - 超出节点/时间预算时**回退到普通策略**，保证不拖慢房间。
- 特征：会算斩杀、会预留防守、会做多步组合。

### 难度可测量（自对弈门槛）

固定种子集合（例如 200 局）下的自对弈胜率目标：

| 对局 | 目标胜率 |
| --- | --- |
| 困难 vs 普通 | ≥ 65% |
| 普通 vs 简单 | ≥ 70% |
| 困难 vs 简单 | ≥ 85% |

另外的硬指标：单机整局**指令拒绝率 < 5%**、每回合指令数 ≤ 预算、单局耗时有上界、同种子重放事件序列逐字节一致。

### 协议变更提案

两处新增，都需要按仓库约定同步 Go DTO、C# DTO、`protocol.md`、固定样例与两端测试：

1. `queue.join` 增加可选字段：
   - `mode`：`ranked`（默认，两人匹配）或 `single`（单机）。
   - `difficulty`：`easy` / `normal` / `hard`，仅 `mode=single` 时有效；缺省按 `normal`。
   - 顺带补上 `queue.status` 的 `state: "matched"`：配对成功的一方目前只收到广播 `match.started`，它的 `queue.join` 永远没有响应（016 已在客户端侧结清，协议侧仍应闭合）。
2. `PlayerView` 增加 `kind`（`human` / `ai`）与 `difficulty`（`kind=ai` 时有值）：客户端据此把对手显示成 `AI（普通）`，观战与回放也能区分。
   - 备选：在 `match.started` 里加 `opponent` 描述对象。否决理由：`PlayerView.kind` 更通用，且两个座位都能被描述。

### 客户端改动

- 顶栏把「进入匹配」拆成两个入口：`联机匹配` 与 `单人对战（简单/普通/困难）`。
- 对手英雄面板显示 `AI（普通）`（来自投影字段），而不是笼统的"对手"。
- 提示行在等待 AI 时沿用"等待对手行动。"（不推断 AI 内部状态）。
- 界面仍然不计算任何规则：难度只是请求参数，合法性仍由服务端裁决。

## 范围与非目标

交付：

- 单机模式的服务端支持（建房 + `botPeer`）。
- 简单、普通、困难三档策略与可测量的难度门槛。
- 协议两处新增及其全部同步项。
- 客户端模式与难度入口、对手类型显示。
- 测试：策略单测、自对弈门槛、确定性、投影安全、单机端到端。

非目标：

- 客户端 AI、AI 作弊（读取隐藏信息）、机器学习或自适应难度。
- 难度影响规则、奖励或排名；排行榜与持久化。
- 观战、AI 托管人类座位（断线代打）。
- 多档难度之外的"教学提示"等教学向功能。

## 风险与回退

| 风险 | 应对 |
| --- | --- |
| bot 死循环或拒绝风暴 | 每回合动作预算 + 被拒动作不重试 + 兜底结束回合 |
| 在 `Send` 内同步提交导致重入 | 驱动放在独立 goroutine，`Send` 只入队 |
| 困难搜索拖慢房间 | 节点/时间硬预算，超预算回退普通策略 |
| 难度调参主观、无法验收 | 用固定种子的自对弈胜率门槛量化；阈值先按上表，允许在 task 里记录调整 |
| 协议变更漏同步 | 按仓库约定在同一个 commit 内改 DTO、文档、样例与两端测试 |
| bot 通过投影泄漏或越权 | 只经 `ViewForSeat` 与 `Manager.Submit`；投影安全有测试 |

回退：保留协议字段（向后兼容、默认联机）并关闭单机入口即可恢复现状；`bot` 包可以整体删除而不影响 `game`/`protocol`。
